# MQTT service

This console manages an MQTT broker (Eclipse Mosquitto): its **clients**, meaning the users that connect, and the **roles** that decide what each client may do.

## Connecting a client

| Setting | Value |
| --- | --- |
| Host | `{{host}}` |
| Port | `{{port}}`, TLS only |
| Protocol | MQTT 3.1.1 or 5 over TLS 1.2 or newer |
| Trust | the CA that signed the broker's certificate (`{{ca_file}}`) |
| Username and password | created in this console |
| Client ID | any value that is unique per connection |
| Keep-alive | 30 to 60 seconds |

Anonymous connections are refused. Plain MQTT without TLS is not available. Two clients that connect with the same client ID disconnect each other.

To try a client from a shell:

```sh
mosquitto_pub -h {{host}} -p {{port}} --cafile {{ca_file}} \
  -u <username> -P <password> -t <topic> -m hello
```

## Access model

Access is granted through **roles**. A role is a list of rules (ACLs); a client can do exactly what its roles allow, and nothing when it has none. Each rule has a type, a topic filter, allow or deny, and a priority:

| Rule type | Controls |
| --- | --- |
| `publishClientSend` | what the client may publish |
| `publishClientReceive` | what the broker may deliver to the client |
| `subscribeLiteral`, `subscribePattern` | which subscriptions the client may make (exact filter, or filters matching a pattern) |
| `unsubscribeLiteral`, `unsubscribePattern` | which subscriptions it may remove |

Topic filters use `+` and `#`, and `%u` and `%c` stand for the client's own username and client ID, so one role can isolate every client to its own topics, for example `devices/%u/#`.

- Roles can be created, edited and deleted here, and several can be given to one client. Give a client the narrowest role that works.
- **Reserved roles** (`admin`, `dynsec-admin` by default) belong to the broker's own administration. They cannot be created, edited, deleted or assigned here, and the clients that hold them are shown as **Protected**.
- No rule can grant the broker's control channel (`$CONTROL`): holding it would let a client rewrite every user and role. Nothing can be granted publishing into `$`-prefixed topics. Reading the broker's statistics (`$SYS`) can be granted.
- A role that clients still hold is not deleted unless you confirm; its clients lose that access immediately. Changing or deleting a role that many clients hold can lock all of them out, so check the client count first.
- Create one client per device or service so each can be disabled on its own, or share one client. Both work; the roles are what grant access.

## Managing clients

| Action | What it does | Strong authentication |
| --- | --- | --- |
| Create | Adds a client with a generated password, shown once | required |
| Disable | Disconnects the client and blocks new connections | not required |
| Enable | Lets a disabled client connect again with its current password | required |
| New password | Replaces the password with a generated one, shown once | required |
| Delete | Disconnects and removes the client permanently | required |
| Add or remove a role | Changes what the client may do | required |

Creating, editing and deleting roles, and their rules, also require strong authentication.

Passwords are generated by the service, shown a single time and never stored by the console. If one is lost, generate a new password and update the client.

## Authentication

Every request to `/admin/api` carries a bearer token: `Authorization: Bearer <token>`. How tokens are issued depends on the service's `ADMIN_AUTH_MODE`:

| Mode | Use it when | Where the token comes from |
| --- | --- | --- |
| `token` (default) | the service runs on its own | a static token generated for you or a job; only its hash is configured |
| `federated` | an identity provider with token introspection is in front | a short-lived token the provider issues per person and action |

In token mode the operator generates a token with `mqtt-admin token new --name <name> --scopes <read|write|admin> [--expires YYYY-MM-DD]` and adds the printed entry to `MQTT_ADMIN_TOKENS`. The token is shown once and cannot be recovered. A token holds scopes, either a preset or single scope names joined with `+`:

| Preset | Grants |
| --- | --- |
| `read` | `mqtt.clients.read`, `mqtt.roles.read`, `mqtt.server.read` |
| `write` | `read`, plus `mqtt.clients.write` and `mqtt.credentials.rotate`; no delete |
| `admin` | every scope, including deleting clients, and creating, editing and deleting roles |

The `write` preset cannot change roles: `mqtt.roles.write` and `mqtt.roles.delete` change who may do what, so they are never part of `write`. Grant them on purpose, for example `write+mqtt.roles.write`.

When the service is called directly, the routes below are under `/admin/api/`, for example:

```sh
curl -H "Authorization: Bearer $TOKEN" https://<admin-host>/admin/api/clients
```

Strong authentication (a recent passkey check before creating, re-enabling, resetting or deleting a client, or changing roles) is not performed by the service. A console or gateway in front of the API can apply it. In token mode a stolen write token is enough, so give people read tokens, keep write tokens for few people or jobs, and set an expiry date.

## API reference

Called directly, these routes are under `/admin/api`; behind a control plane they may be exposed under another prefix such as `/api/mqtt`. Each route needs one scope.

| Method and path | Scope |
| --- | --- |
| `GET /server` | `mqtt.server.read` |
| `GET /stats` | `mqtt.server.read` |
| `GET /roles` | `mqtt.roles.read` |
| `GET /roles/{name}` | `mqtt.roles.read` |
| `POST /roles` | `mqtt.roles.write` |
| `DELETE /roles/{name}` | `mqtt.roles.delete` |
| `POST /roles/{name}/acls` | `mqtt.roles.write` |
| `POST /roles/{name}/acls/remove` | `mqtt.roles.write` |
| `GET /clients` | `mqtt.clients.read` |
| `GET /clients/{username}` | `mqtt.clients.read` |
| `POST /clients` | `mqtt.clients.write` |
| `POST /clients/{username}/disable` | `mqtt.clients.write` |
| `POST /clients/{username}/enable` | `mqtt.clients.write` |
| `POST /clients/{username}/password` | `mqtt.credentials.rotate` |
| `PUT /clients/{username}/roles/{role}` | `mqtt.roles.write` |
| `DELETE /clients/{username}/roles/{role}` | `mqtt.roles.write` |
| `DELETE /clients/{username}` | `mqtt.clients.delete` |
| `GET /docs` | `mqtt.server.read` |
| `GET /docs/{version}` | `mqtt.server.read` |

Usernames use letters, digits, `.`, `_` and `-`, start with a letter or digit, and are at most 128 characters. Errors are returned as `{"error":"<code>"}`:

| Code | Meaning |
| --- | --- |
| `unauthorized` | the token is missing, expired or invalid |
| `forbidden` | the token is for another service or lacks the scope |
| `protected_user` | the client is protected and cannot be changed |
| `invalid_username` | the username does not follow the rule above |
| `role_not_allowed` | the role cannot be assigned through the API |
| `role_required` | no role was given and there is no single default |
| `invalid_role` | the role name does not follow the rule |
| `reserved_role` | the role is reserved and cannot be edited or deleted |
| `role_in_use` | clients still hold the role; repeat with `?force=true` to delete it anyway |
| `invalid_acl` | the rule's type, topic filter or priority is invalid |
| `forbidden_topic` | the rule would grant the control channel or publishing into `$` topics |
| `invalid_description` | the description is too long or has control characters |
| `already_exists` | a client or role with this name exists |
| `not_found` | no client or role with this name |
| `broker_unavailable` | the service cannot reach the broker |
| `too_many_failures` | too many refused requests from one address; wait a minute |

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| A client cannot connect, TLS error | The client does not trust the broker's CA, or the host name is not `{{host}}` |
| Connection refused with a bad user name or password | The client is disabled, the password changed, or the name has a typo |
| Connected, but nothing arrives | The client published or subscribed on topics its roles do not allow, or on different topics than its peers |
| Two clients keep disconnecting | They share a client ID |
| The console shows the broker as unavailable | The administration service lost its broker connection; it recovers on its own, otherwise check the broker project |
